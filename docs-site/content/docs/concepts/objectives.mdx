## Objectives

An objective is the top-level unit of work in Tack. You describe what you want built, optionally choose a blueprint, and Tack starts the workflow for the current project.

```bash
tack plan "Add pagination to all list endpoints"
tack plan "Add pagination to all list endpoints" --blueprint standard
```

The default workflow is:

```text
objective created -> planner runs -> plan ready -> human approval -> execution -> merge/pr
```

## The Planner

When you submit an objective, Tack spawns a planner agent. The planner:

1. Explores your codebase to understand its structure
2. Identifies what needs to change
3. Decomposes the objective into independent streams
4. Assigns file scopes and dependencies to each stream

The planner outputs a structured plan that Tack validates and presents for your review.

Tack's roadmap pushes this further: discovery and a context dossier are expected to become planner inputs so planning starts from researched, cited context instead of raw objective text alone.

## Plan Approval

Plans require human approval before execution begins:

```bash
tack show <plan-id>    # Review streams, file scopes, dependencies
tack approve <plan-id> # Start execution
tack reject <plan-id>  # Return to planning
```

## Work Items And Streams

Plans are made of streams: parallel work items with file scopes, dependency ordering, and isolated execution.

Public docs and CLI still talk about **streams** because they are the execution unit you see in plans, watch output, and merge state.

In blueprint YAML, nested execution now uses `foreach: work_item` to describe per-item fanout without baking old starter blueprint names into the public model.

## Blueprint Selection

```bash
tack plan "Fix the typo in README.md" --blueprint standard
```

If you omit `--blueprint`, Tack resolves the default blueprint from the blueprints loaded for the targeted project.
