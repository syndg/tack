## What is a Blueprint?

A blueprint is a YAML state machine that defines a Tack workflow. Filenames are arbitrary. The public identity is the blueprint `id`.

Steps can be:

| Type | Description |
|------|-------------|
| `agent` | Spawns an AI agent such as planner, scout, builder, or reviewer |
| `deterministic` | Runs infrastructure logic such as dispatch, gates, merge, or PR creation |
| `human` | Pauses for human approval |
| `blueprint_ref` | Runs another blueprint by `id` |

## Default Blueprints

Tack ships two default blueprints:

### `standard`

The default top-level workflow. It plans, waits for approval, dispatches work, runs the nested build-review workflow for each work item, merges, and opens a PR.

### `build-review`

The nested per-work-item workflow.

```yaml
id: build-review
name: Build and review

retry:
  profile: self_healing

steps:
  - id: build
    type: agent
    role: builder
    commit: auto
    messages:
      commit: true
    next: lint

  - id: lint
    type: deterministic
    action: run_quality_gates
    retry:
      max_attempts: 2
    on_fail: build
    max_fix_iterations: 3
    next: review

  - id: review
    type: agent
    role: reviewer
    commit: none
    on_fail: build
    max_fix_iterations: 3
    next: merge_ready

  - id: merge_ready
    type: deterministic
    action: signal_merge_ready
```

The shipped top-level blueprint references the nested one by `id`:

```yaml
id: standard
default: true
steps:
  - id: execute
    type: blueprint_ref
    ref: build-review
    foreach: work_item
    on_work_item_failure: escalate
```

## Customizing Blueprints

Blueprints are loaded per project with this precedence:

1. embedded defaults
2. `~/.config/tack/blueprints/`
3. `<repo>/.tack/blueprints/`

Later definitions win **by blueprint `id`**, not by filename.

Override the default `build-review` workflow by defining your own blueprint with `id: build-review`:

```yaml
# .tack/blueprints/review-lite.yaml
id: build-review
name: Review lite

retry:
  profile: balanced

steps:
  - id: build
    type: agent
    role: builder
    commit: auto
    next: lint

  - id: lint
    type: deterministic
    action: run_quality_gates
    retry:
      max_attempts: 3
    on_fail: build
    max_fix_iterations: 5
    next: merge_ready

  - id: merge_ready
    type: deterministic
    action: signal_merge_ready
```

This example keeps the public workflow identity the same while changing the implementation for the current project.

## Default Resolution

When an objective starts, Tack resolves the blueprint like this:

1. If the objective explicitly requested a blueprint, use that `id`.
2. Otherwise, if exactly one blueprint is loaded, use it.
3. Otherwise, exactly one loaded blueprint must set `default: true`.

If no default exists, or more than one blueprint is marked default, Tack returns an error until you fix the registry or choose a blueprint explicitly.

## Step Options

### Agent Steps

- `role` — agent role (planner, builder, reviewer)
- `commit` — commit mode: `auto` (default), `agent`, or `none`
- `model` — optional model override for that step
- `messages` — structured outputs the agent should generate such as commit or PR text
- `message_source` — where structured messages should be derived from
- `on_fail` — reroute target for agent-driven repair loops such as `review -> build`
- `max_fix_iterations` — cap on reroute-driven repair loops
- `tools` — optional tool scope restrictions
- `optional` — allow the step to be skipped without failing the run

### Deterministic Steps

- `action` — the action to run: `dispatch_streams`, `run_quality_gates`, `signal_merge_ready`, `merge_queue`, `create_pr`, `mark_complete`
- `retry.max_attempts` — retry budget for that step
- `retry.on_exhausted` — what to do when retry budget is exhausted
- `retry.human_guidance_mode` — how human guidance should be attached on resume
- `on_fail` — step to jump to on failure (fix-loop)
- `max_fix_iterations` — cap on fix-loop cycles

### Top-Level Retry Config

Blueprints can define a narrow recovery posture at the top level:

```yaml
retry:
  profile: balanced
  default_max_attempts: 4
  default_on_exhausted: ask_human
```

The built-in profiles are:

- `strict`
- `balanced`
- `self_healing`

### Human Steps

Pause execution until a human approves via `tack approve` or the API.

### Blueprint Reference Steps

- `ref` — nested blueprint `id`
- `foreach` — currently `work_item`
- `on_work_item_failure` — `escalate` or `fail`
- `escalation.context` — `full`, `minimal`, or `error_only`
- `escalation.include_agent_history` — include worker history in the escalation payload
