Tack is an open-source harness for deterministic, repository-aware agentic code execution. It is not just another agent orchestrator. You describe what you want built, and Tack turns that objective into a bounded workflow: planning, isolated execution, deterministic checks, recovery, merge, and PR creation.

You go from being the developer to being the team lead.

The agents are workers. Tack is the programmable harness around them.

```bash
$ tack plan "Add pagination to all list endpoints and a PATCH /expenses/:id endpoint"

Created objective fb68742b. Planner agent will decompose.

$ tack approve e2b12fee

Plan approved. Execution will begin.
  Stream 1: PATCH expenses endpoint        ██████████ merged
  Stream 2: Pagination for list endpoints   ██████████ merged

Objective completed. PR created: github.com/you/project/pull/42
```

## Why Tack

**The harness matters more than the model.** Tack treats the model as a worker and the harness as the product: blueprints, scoped rules, quality gates, merge policy, isolation, escalation, and observability are deterministic infrastructure you control.

Everything in Tack that isn't an LLM decision is deterministic infrastructure: the blueprint engine, quality gates, merge queue, scoped rules, file scope enforcement, timeout management. The LLM is the horse. Tack is the equipment.

Tack is trying to make repositories legible to agents and make agent execution reliable through infrastructure, not vibes.

## Current Shape

- **Daemon-first.** `tack daemon` is a machine-wide service.
- **Project-scoped.** Each repo gets a stable `project_id`, local `.tack/` config, rules, and blueprints.
- **Blueprint-driven.** Workflow steps are explicit YAML state machines, not hidden prompts.
- **Isolation-first.** Agents run in separate worktrees or remote sandboxes.
- **Deterministic where it matters.** Quality gates, merge ordering, scoped rules, and retries are infrastructure concerns.
- **Recovery-aware.** Gate failures, reviewer rejection, and restart recovery are first-class parts of the workflow.

## Recovery Model

Tack records recovery attempts durably and uses them to drive reruns.

- Quality gate failures rerun the builder with gate output attached
- Reviewer rejection reruns the builder with reviewer feedback attached
- Transient runtime failures retry the same step in place
- Exhausted retries can block for human guidance instead of failing permanently
- Human-guided retries survive daemon restarts and resume from the correct point

## What Exists Today vs What Is Planned

**Exists today:**

- machine-wide daemon with project-scoped execution
- explicit blueprints, isolated sandboxes, and deterministic quality gates
- planner -> approval -> build/review -> merge flow
- recovery-aware execution with watch/log/mail surfaces

**Planned next:**

- a first-class discovery step before planning
- compact context dossiers
- bounded execution contracts per work item
- stronger benchmark-driven evaluation for context quality

Tack's direction is to make the context packet better, not just add more workers.

## Where Tack Is Going

Tack's next focus is **context engineering** and **harness hardening**.

That means improving the step before planning: discovery, compact context dossiers, bounded execution contracts, and better repo legibility. The goal is not just "run more agents". The goal is to give each worker the smallest, highest-signal packet possible.

## What Tack Is Not

- **Not just another agent orchestrator.** Spawning workers is table stakes. The differentiator is the harness around them.
- **Not an agent framework.** Pi and Claude Code do the thinking. Tack shapes the workflow around them.
- **Not a sandbox provider.** Local worktrees, Daytona, Docker provide isolation. Tack manages their lifecycle.
- **Not an IDE.** Agents edit code. You review their work.
- **Not a CI system.** Tack runs quality gates locally in sandboxes. CI is your existing pipeline.
- **Not locked to any model.** Bring your own runtime, provider, and model.
